# Internationalization (i18n)

This guide covers reusable package strings and contributor checks. Application
copy, catalog descriptions and Docs translations belong to their owning apps.

## Package Scope

Keep reusable messages from [Config classes](../insight_ui/configs/),
[templates](../insight_ui/templates/insight_ui/) and
[JavaScript](../insight_ui/static/insight_ui/js/) in the package.
The catalog location is `insight_ui/locale/<locale>/LC_MESSAGES/`: `django.po`
for Python/templates and `djangojs.po` for JavaScript. This revision has marked
strings but no checked-in locale catalogs, so language coverage is not implied.
Create that directory when contributing translations; do not import Docs catalogs.

Consumers install `insight_ui` in `INSTALLED_APPS`, enable `USE_I18N`, and own
`LANGUAGE_CODE`, `LANGUAGES` and request-language selection. Project-specific
`LOCALE_PATHS` are not a substitute for the package's app-local catalogs.
See [Django translation setup](https://docs.djangoproject.com/en/6.0/topics/i18n/translation/).

## Mark Python And Template Strings

Use `gettext_lazy` for Config values, import-time defaults and translated field
metadata, following [base Config fields](../insight_ui/configs/base.py):

```python
from django.utils.translation import gettext_lazy as _
from insight_ui.configs import InputFieldConfig

email = InputFieldConfig(
    tag_id="email", name="email", label=_("Email address"), required=True,
)
```

For new dataclass fields, mark documentation too, for example
`field(default="", metadata={"doc": _("Visible label.")})`.
Do not force lazy values to `str` at import time. Translate human-facing labels
and accessible names, not IDs, field names, URLs or enum values.

Load Django's `i18n` tags in every template that uses them. Use a literal message
with `trans`, or `blocktranslate` for complete sentences and plural forms:

```django
{% load i18n %}
<button type="button">{% trans "Continue" %}</button>
<p>{% blocktranslate trimmed with name=display_name %}
  Hello, {{ name }}!
{% endblocktranslate %}</p>
<p>{% blocktranslate trimmed count total=items|length %}
  {{ total }} item selected
{% plural %}
  {{ total }} items selected
{% endblocktranslate %}</p>
```

Keep placeholders named and identical across translations; do not concatenate
sentence fragments or pass f-strings into gettext. Use `ngettext` for Python
runtime plurals, or `ngettext_lazy` for deferred plurals, rather than assuming
every language has only singular/plural. Add translator comments for ambiguity.
Leave template escaping enabled; translations are not a reason to use `safe`.

## Generate And Compile Catalogs

Complete the environment setup in [Contributing](../CONTRIBUTING.md) first.
Install GNU gettext and put `xgettext`, `msgmerge`, `msguniq` and `msgfmt` on
`PATH`; Django does not bundle these tools. Run extraction from the **package
directory**, not the repository root or a Docs checkout:

```bash
# Start at the insight-ui repository root with .venv prepared.
cd insight_ui
mkdir -p locale
../.venv/bin/python -m django makemessages -l de
# Also run this when changing JavaScript gettext/ngettext messages:
../.venv/bin/python -m django makemessages -d djangojs -l de --ignore='*.min.js'
# Translate locale/de/LC_MESSAGES/django.po and, if generated, djangojs.po.
../.venv/bin/python -m django compilemessages -l de
cd ..
```

Replace `de` with the target locale. These standalone Django commands need no
Docs settings or `manage.py`; leave `DJANGO_SETTINGS_MODULE` unset for this
workflow. [Django's command reference](https://docs.djangoproject.com/en/6.0/ref/django-admin/#makemessages)
explains extraction options. The [devtools CLI](../devtools/__main__.py) only
dispatches `create_component` and `preview`, not translation commands.

Review `.po` changes, translator headers, plural rules and placeholders before
compiling `.mo` files. Resolve fuzzy entries after checking their translations;
compilation skips fuzzy messages by default. Successful compilation is not proof
of complete coverage, and a bare `msgstr ""` can introduce a multiline value.
Keep extraction limited to package sources and review the resulting diff.
Compiled `.mo` files are ignored build outputs in [.gitignore](../.gitignore);
do not force-add them or assume local compilation proves wheel delivery.

## Test Translated Rendering And RTL

Add focused [package render tests](../tests/insight_ui/unit/components/) using
`django.utils.translation.override("de")` around the real Config/template tag.
After compiling a translation, assert its expected visible text and accessible
name, not just that rendering succeeds. Cover missing translations, long labels,
escaping and counts including zero, one, two and the locale's other plural cases.
For JavaScript messages, test the host's language-specific `JavaScriptCatalog`
and interpolation as well as server-rendered text.

The [package base template](../insight_ui/templates/insight_ui/base.html) gets
`lang` from Django's active language and `dir` from `LANGUAGE_BIDI`. Render it
with a request and the i18n context processor, or explicitly supply direction in
an isolated test. Under `override("ar")`, check `lang="ar"` and `dir="rtl"`.
Direction alone does not prove translation coverage or complete RTL support.
Inspect wrapping, logical start/end spacing, directional icons and drawer motion
in a browser; verify keyboard order rather than mechanically reversing all keys.

The [preview settings](../devtools/settings.py) have no `LocaleMiddleware` or
real application authentication; the [preview shell](../devtools/templates/devtools/preview.html)
hard-codes `lang="en"` and has no direction switch. Changing browser language
does not make it a translated-app test. Use render overrides or a separate
integration host for language switching, authenticated flows and RTL evidence.
See also the [accessibility guide](accessibility.md).
